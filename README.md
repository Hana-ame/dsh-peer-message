# dsh-peer-message

A global P2P messaging plugin for the DeepSeek Harness (DSH) Web UI. It adds a
WeChat/QQ-style chat panel that connects two DSH Web tabs over **PeerJS**, so a
user can discover a friend by **string peer ID** or by **QR code** and exchange
messages in real time. It also ships an **agent preset** (`Peer Chat`) that lets
a session's agent send P2P messages through the `pm_send` tool, alongside
`web_search` and `web_fetch`.

## Features

- **Global chat panel** — a sidebar icon opens a friend list with avatars,
  nicknames, last-message previews, and unread-count badges.
- **QQ / WeChat style** — chat bubbles, message input, friend management.
- **Safe friend management** — right-clicking a friend opens an action menu
  (open chat / copy ID / mark as read / delete). Deleting needs a second
  confirmation, so a stray right-click can never wipe a friend and its history.
- **PeerJS connectivity** — two DSH Web tabs (or two machines) exchange
  messages directly over the PeerJS cloud signaling server.
- **Discovery by string ID** — share your peer ID and add a friend by typing
  theirs.
- **Discovery by QR code** — render your peer ID as a QR code for another
  device to scan; accept an incoming connection.
- **Unread-count badges** — each friend row shows the number of unread messages.
- **Night-mode compatible** — the UI styles use `--dsw-alias-*` design tokens,
  so it adapts to the active DSH theme (light/dark).
- **Local public-key identity** — identity is an **ECDSA P-256 keypair generated
  locally** and stored only in this browser. The PeerJS ID is derived from the
  public-key fingerprint (`dsh-pm-<40 hex>`), and the `hello` handshake carries
  the public key, fingerprint and a signature; the peer verifies the ID↔key
  binding before marking the friend 🔐 **身份已验签**. The identity is also
  **persistently visible**: a sidebar identity row and the sidebar icon show the
  short fingerprint even when the panel is closed, the QR dialog shows the full
  fingerprint, and verified friends keep 🔐 + the fingerprint in their chat
  header across reconnects and restarts. No random ID to reset.
- **Display names and remarks** — set your own nickname (sent over the `hello`
  handshake in both directions) and give friends local-only remarks that always
  win over the nickname their client sends.
- **Friend notes injected into the reply context** — each friend can carry a
  longer note (≤500 chars); it is injected into the auto-reply prompt as a
  trusted local `<peer_note>` block, while the peer message itself stays fenced
  as untrusted content.
- **Model vs human provenance** — messages written by a person look different
  from messages generated by a model; AI messages carry a badge saying whether
  the model decided to send it, a human approved it, or an Agent sent it.
- **Agent `pm_send` tool** — a `Peer Chat` agent preset exposes `pm_send`
  (queue a P2P message to a peer), `web_search`, and `web_fetch`, with the
  global tools (`bash`, `fs`, `browser_*`, `plugin_manager`, …) hidden.
- **Agent auto-reply callback** — inbound friend messages can trigger one
  agent turn that answers back over P2P: off / manual-approve / fully
  automatic, with a five-level capability gate, endpoint + model selection,
  per-peer dedicated or shared existing session, and a configurable working
  path. See [Agent auto-reply](#agent-auto-reply).

## Friend management

Right-click a friend row to open its action menu:

- **打开聊天** — select the friend and jump to the conversation.
- **复制 Peer ID** — copy the friend's Peer ID to the clipboard.
- **标记已读** — clear that friend's unread badge (disabled when already read).
- **删除好友…** — opens a confirmation dialog; the friend and its message
  history are only removed after you confirm.

`Escape`, clicking outside, resizing, or scrolling closes the menu without
changing any data; `Escape` or **取消** dismisses the delete dialog. The menu is
anchored at the pointer and clamped to the viewport, so right-clicking near the
bottom-right corner still leaves every menu item clickable.

## Agent auto-reply

The sidebar ⚙ button opens **P2P 自动回复设置**. When enabled, every inbound
text message from a friend is handed to the Host half of the bundle, which runs
one agent turn and sends the final answer back to that peer over P2P. The
browser half never executes tools or models itself: it only POSTs the untrusted
message to the Host and displays the result.

### Reply modes

| Mode | Behavior |
| --- | --- |
| 关闭 (`off`) | No agent call at all (default). |
| 手动批准 (`manual`) | Inbound messages land in the pending queue; nothing runs until you click **批准回复**. **忽略** drops the request. |
| 全自动 (`auto`) | Each inbound message runs a reply turn immediately, bounded by the rate limits below. |

### Capability modes (permission of the reply agent)

| Mode | Sandbox / approval appended to the session | Tool gate (`tools/pre-execute`) |
| --- | --- | --- |
| 全不允许 (`deny-all`) | `read-only` + `ask` (defense in depth) | denies **every** tool |
| 只读 (`read`) | `read-only` + `ask` | allows `read`, `read_image`, `glob`, `grep`, `web_search`, `web_fetch` only |
| 只写 (`write`) | `workspace-write` + `ask` | allows `write`, `edit`, `present` only |
| 读写 (`readwrite`) | `workspace-write` + `ask` | every tool; writes stay inside the session workspace |
| 全自动 (`auto`) | `danger-full-access` + `never` | every tool, no approval prompts |

The gate is enforced by the Host plugin on `tools/pre-execute`; the sandbox /
approval pair is appended to the session log as a second layer. `deny-all`
still lets the model answer from its own knowledge, it just cannot touch any
tool.

### Model, endpoint, session, working path

- **Endpoint + model** — picked from the live `modelCatalog()` (all configured
  providers and routable models, plus reasoning-effort choices when offered).
  Leaving both empty uses the session / deployment default.
- **Session** — `dedicated` (default) creates one session per friend and reuses
  it for later replies, preserving context; `existing` injects the message into
  a session you pick from the session list. In `existing` mode the capability
  pair is applied for the reply turn and then restored; the session's current
  model may be switched to the configured endpoint/model.
- **Working path** — absolute `cwd` for dedicated sessions; pick one of the
  registered workspaces or type any absolute existing directory.

Pending approvals, running turns, and recent results are polled every 2.5 s and
shown in the panel (a badge appears above the friend list). Settings persist in
the same `localStorage` state as friends/messages (`settings.reply`).

### Security model

Inbound P2P text is untrusted:

- the prompt fences the message in `<incoming_p2p_message>` and explicitly
  forbids following instructions from the body; literal fence tags in the body
  are defanged so they cannot break out of the envelope;
- the browser sends plain text only; the Host re-validates peer ID, text length
  (§4096), config enums and pending caps;
- per-peer cooldown (5 s), per-peer window (6/min) and global window (20/min)
  bound model spend; at most 20 requests can wait for approval;
- replies are prefixed with `[自动回复] ` so the receiver can tell the message
  is AI-generated, and a message already carrying that marker never triggers
  another reply — two auto-replying peers cannot ping-pong forever;
- only text from existing friends triggers a callback; `hello` handshakes,
  objects, empty and control-only payloads are ignored.

Limits worth knowing: P2P lives in the browser, so a reply can only run while a
DSH Web tab is open; the pending queue is in Host memory (lost on restart); the
per-peer dedicated-session mapping is per DSH process (after a restart the next
message may create a new session); `auto` mode is a genuine remote-code path —
only enable it for peers you trust.

### Host routes

| Route | Method | Purpose |
| --- | --- | --- |
| `/api/pm-reply/request` | POST | browser reports one inbound message (`peerId`, `text`, `config`) |
| `/api/pm-reply/requests` | GET | pending / running / recent reply state |
| `/api/pm-reply/approve` | POST | run one parked manual request |
| `/api/pm-reply/reject` | POST | drop one parked manual request |
| `/api/pm-reply/catalog` | GET | endpoints/models, sessions, workspaces for the settings UI |

## Display names, remarks, and Peer ID

### Your display name

The sidebar shows **显示名称** under your peer ID; the ✎ button edits it (max 32
characters, empty = use the peer-ID prefix). The nickname is persisted in
`settings.nickname` and sent as `{type:"hello", name:…}` when a connection
opens — from both the dialing and the accepting side, so each peer knows the
other's name. Editing it broadcasts a fresh `hello` to all live connections.
Defaults are never a hard-coded "我" any more.

### Friend remarks and context notes

Right-click a friend → **编辑备注…**. The dialog has two local-only fields:

- **显示备注名** (`friend.alias`, ≤32 chars) — what you see instead of the
  nickname the other side sends. It always wins over `hello`, which only updates
  `friend.name`. Display priority: `alias` → received `hello` name → peer-ID
  prefix. Search matches all three.
- **备注内容** (`friend.note`, ≤500 chars) — injected into the auto-reply model
  context whenever that friend's message triggers a reply. It is rendered as a
  trusted local block *before* the untrusted message:

  ```
  <peer_note>
  …your note…
  </peer_note>
  <incoming_p2p_message>
  …peer message (untrusted)…
  </incoming_p2p_message>
  ```

  The note can carry identity hints and回复偏好 (e.g. "这是同事王工，称呼他王工，
  回复简洁"). Literal fence tags inside the note are defanged, the note is length
  bounded, and the security rules explicitly outrank both the note and the
  message body. The pending-approval dialog shows the note next to the request
  so a human approver sees the same context; friends with a note show a 📝
  marker in the list.

### Message provenance (human vs model)

Every message keeps a structured origin, not just a text prefix:

| Wire text | Meaning | Local badge |
| --- | --- | --- |
| plain text | a person typed it | none |
| `[自动回复] …` | model auto-reply (auto mode) | `AI · 自动回复` |
| `[自动回复] [人工批准] …` | model reply a human approved | `AI · 你已批准` |
| `[AI] …` | model-authored `pm_send` Agent message | `AI · Agent 发送` |

Incoming messages are classified the same way, with the marker stripped from the
bubble body and replaced by `AI · 对方自动回复` / `AI · 人工批准` / `AI · 对方
Agent`. The friend-list preview is prefixed with `AI｜` for the last message when
it came from a model, and pending approvals show `AI · 模型生成 · 待批准`.
Model-marked messages never trigger another auto-reply, so two AI peers cannot
ping-pong. The outbox also carries `meta: {origin, trigger, model}`; queue items
written by older versions without meta (or without a marker) are treated as
model/Agent messages, since only agent-side code writes the outbox.

### Keypair identity and ID occupancy

Identity is not a random string any more:

1. On first use the client generates an **ECDSA P-256 keypair** with WebCrypto
   and stores the private JWK in `localStorage`
   (`dsh-peer-message-identity-v1`, local only — never transmitted).
2. The **Peer ID is derived from the public-key fingerprint**:
   `dsh-pm-` + first 40 hex chars of `SHA-256("EC|P-256|<x>|<y>")`. The same key
   always yields the same ID; different keys cannot collide in practice.
3. `hello` carries `{name, pub, fp, sig}` where `sig` signs the canonical
   `{v,id,fp,name}` payload. The receiver verifies:
   - fingerprint recomputed from `pub` equals `fp` **and** `conn.peer ===
     "dsh-pm-" + fp` (PeerJS ID ↔ key binding),
   - the signature verifies against `pub`.

   Success stores `friend.pubKey/fingerprint` and shows 🔐 + “身份已验签”;
   failure closes that connection, shows “身份校验失败（签名无效/公钥与 Peer ID
   不匹配）” and marks the friend unverified. Peers on older versions that send a
   `hello` without `pub` are still compatible but shown as **未验签**.

Because the Peer ID is deterministic from the shared local key, two tabs would
race for one PeerJS ID. The plugin does **not** randomize the Peer ID to escape
that; it coordinates a single connection owner instead:

- Every tab requests an exclusive **Web Lock**
  (`dsh-peer-message-network-owner`). The lock holder becomes the only **leader**
  that creates the PeerJS connection with the key-derived Peer ID. Other tabs are
  **followers**: they mirror the leader's persisted state through `storage`
  events and forward user actions (send, add/remove friend, notes, settings)
  through a `BroadcastChannel`.
- Identity creation is serialized by its own Web Lock
  (`dsh-peer-message-identity`), so two tabs opened at the same moment cannot
  each generate a different keypair.
- The sidebar shows the role: `🔗 连接由本标签页持有` or `🔗 连接由其他标签页持有 ·
  操作自动转发`. Closing the leader releases the lock; a follower takes over
  with the **same key and the same Peer ID**.
- On `unavailable-id` the same Peer ID is retried automatically with backoff.
  The banner offers **重试连接** (force-recreate the same identity/Peer ID) and
  **身份密钥** (fingerprint view). It does **not** generate a new random Peer ID.
  If another DSH process/window outside this browser uses the same identity,
  close it. The identity dialog keeps a deliberate
  **轮换身份密钥（会更换身份与 Peer ID）** action for a genuine identity change —
  it is not the fix for an occupied ID.
- Without Web Locks (non-secure context) each tab runs standalone and collisions
  are possible again. A WebCrypto-less page falls back to the legacy random Peer
  ID with `secured=false` and peers see it as unverified.

Private keys are **not** exported by the UI; anyone with a backup of the browser
profile can impersonate this identity, so do not share it.

### Persistent identity display

The identity is not hidden inside a dialog:

- **Sidebar row** — `🔐 身份已启用 · 指纹 07b9…bb3b`, always visible next to the
  display name; hover/click opens the full fingerprint and rotation dialog. On a
  non-secure page it shows `⚠️ 身份未启用（非安全上下文）`.
- **Sidebar icon** — a small 🔐 badge is rendered even when the message panel is
  closed, so the toolbar always reflects that a key identity is active.
- **QR dialog** — shows the full grouped public-key fingerprint under the Peer
  ID, so sharing a QR also shares the identity you can read out loud.
- **Friend chat header** — after verification: `在线 · 身份已验签 · 指纹
  07b9…bb3b`; the full fingerprint is in the title attribute. The `🔐` badge and
  stored fingerprint persist in the friend record while offline and across
  restarts; each reconnect re-verifies the signed `hello`.
- **Identity dialog** — Peer ID, `ECDSA P-256 / SHA-256`, full fingerprint,
  copy-fingerprint and key rotation.


## Installation

This is a DSH bundle. From a DSH Web profile:

```bash
# add the dependency
npm install --save /path/to/dsh-peer-message
```

Then enable the bundle `dsh-peer-message` and the preset bundle
`dsh-peer-preset` in the DSH plugin manager, or declare the preset's plugin:

```yaml
# dsh-peer-preset/cordis.patch.yml
- insert:
    - id: preset-peer
      name: '@deepseek-ai/dsh-agent-preset'
      config:
        id: peer
        name: Peer Chat
        description: Web search, web fetch, and P2P chat only.
        order: 20
        plugins:
          - id: persona
            name: '@deepseek-ai/dsh-persona'
            config:
              prefix: You are a peer-chat assistant with web search and P2P messaging. Use web_search/web_fetch for research, and pm_send to message a friend peer.
          - id: tool-web
            name: '@deepseek-ai/dsh-tool-web'
            config:
              fetch: true
              searchTimeoutMs: 60000
          - id: peer-tool
            name: 'file:///abs/path/dsh-peer-message/tool.js?rev=1'
```

## How it works

```
 agent (pm_send)          client poll (600ms)          PeerJS
  ┌──────────┐  push  ┌──────────────────┐  GET   ┌────────────┐
  │ tool.js  ├───────►│ /api/pm-outbox   ├───────►│  outbox.js │
  └──────────┘        │ (Host index.js)  │        └─────┬──────┘
                      └──────────────────┘              │ deliver over PeerJS
                                                        ▼
                                                friend's DSH Web tab
```

- `tool.js` (preset plugin) registers the `pm_send` tool. When an agent calls
  it, the message is pushed into the shared `outbox.js` queue.
- `index.js` (Host plugin) registers the `GET/POST /api/pm-outbox` fetch route.
  The client polls it every 600 ms to drain queued messages and re-queue any
  delivery failure.
- `client.js` (client plugin) owns the chat panel UI, PeerJS connectivity, and
  localStorage persistence.

The fetch route lives in the Host plugin (not the preset) because a fetch route
is process-global; keeping it in the preset would orphan it across preset HMR
reloads.

## Development

```bash
npm test   # runs test/*.test.js
```

Host-side files (`index.js`, `reply-core.js`, `reply-runner.js`) are ESM
modules imported by the DSH Host loader. A running `dsh web` only re-reads
bundle patch layers on restart, so host changes need either a DSH restart or a
deliberate hot-mount during development (a `file:///…/index.js?rev=<new>`
insert row in the Home patch layer, see `$DSH_HOME/cordis.patch.yml`). The
relative `reply-runner.js?rev=` import in `index.js` exists to bust Node's ESM
cache under that hot-mount workflow; bump it when editing `reply-runner.js`.
Client plugin changes hot-reload automatically.
